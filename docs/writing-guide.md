# 문서 작성 기준

게임 이름은 `PokeSurvivor`로 표기합니다.

소개 글은 무엇을 설치하는지, 어떻게 쓰는지, 어디까지 번역하는지부터 설명합니다. 설치 순서는 번호 목록으로, 서로 비교할 항목은 표로 씁니다. 나머지는 짧은 문단이면 충분합니다.

문장을 넣기 전에 사용자의 선택이나 다음 행동에 필요한지 확인합니다. API key, 번역 서버, 내부 데이터 구조처럼 설치와 플레이에 필요 없는 설명은 개발 문서에 둡니다. 필요 없는 기술을 나열하며 “없어도 된다”고 설명하지 않습니다.

- “익숙한”, “간편한” 같은 평가 대신 실제 동작을 적습니다. 예: “간편한 전환” → “게임 설정이나 Chrome 툴바에서 한국어를 켜고 끕니다.”
- 같은 설명을 제목, 소개, 기능 목록에서 반복하지 않습니다. 새 정보가 없는 도입이나 결론은 덜어냅니다.
- “동적으로 나타나는 메뉴”처럼 개발 용어가 필요 없는 곳은 “플레이 중 새로 나타나는 메뉴”로 풀어 씁니다.
- 자연스러워 보이려고 감탄문, 반문, 체험담을 덧붙이지 않습니다. 확인하지 않은 경험이나 효과도 쓰지 않습니다.
- 문구를 고쳐도 숫자, 제품명, 명령, 경로, 설치 조건, 번역 제외 범위와 라이선스는 유지합니다.
- 검색에 쓰일 이름은 제목과 소개에 자연스럽게 넣습니다. 같은 검색어를 반복하거나 따로 늘어놓지 않습니다.

## 참고한 자료

[GOV.UK의 쉬운 문장 지침](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/clear-language/)은 익숙한 단어로 실제 행동을 설명하고, 필요한 전문 용어는 풀어 설명하도록 권합니다.

[NN/g의 웹 글쓰기 연구](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/)는 간결하고 훑어보기 쉬운 글, 과장 없이 사실을 전하는 글을 비교했습니다. 1997년 웹 사용성 연구이므로 AI 문체를 판별하는 근거로 쓰지는 않습니다.

[Crosthwaite·Sun·Jiang의 연구](https://doi.org/10.1111/modl.70089)는 영어 논증문에서 프롬프트에 따라 AI의 문체가 크게 달라지고, 독자에게 말을 거는 표현 등을 주문하면 오히려 정형화된 표현이 늘 수 있음을 보고했습니다. 이를 특정 한국어 표현이 AI가 쓴 증거라는 뜻으로 일반화하지 않습니다.
